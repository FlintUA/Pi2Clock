# Browser Bluetooth speaker management

Status: implemented and software-tested on the development branch; installation and user acceptance pending.

## Workflow

The Bluetooth speakers panel lists saved devices first, followed by discovered devices, with one row per address. Names are shown; addresses are internal action identities and USB diagnostics. Equal or changing names do not change the identity of a selected speaker. A saved speaker can be connected without scanning. Connect requests the existing Classic Bluetooth pairing/A2DP path; status distinguishes connecting/retrying from an active stream. Acceptance of a command is not proof of a successful connection. Selecting the already connected device does not restart its stream.

Scan devices intentionally disconnects the current target and saves manual OFF using the existing policy. The panel shows discovery/name-resolution progress and partial results; wait for completion or use Cancel scan. Completing/cancelling a scan does not restore the former speaker. Disconnect retains saved entries and pairing keys, and retains OFF after autosave/restart until explicit Connect. Forget saved speaker requires a browser confirmation and removes the selected saved entry/key. Forgetting the selected target also clears its pending/saved selection. Wait for Settings saved before power-off.

There are four saved slots. The browser requires explicitly forgetting one saved speaker before connecting a new discovered device when all four are occupied. It never silently evicts an entry. This is a deliberate web admission rule; existing physical/USB selection retains its earliest-added replacement policy. A new browser choice is saved only after a matching active stream, using the existing main-loop persistence logic. Saved-name retention, address deduplication, reconnect policy and retry intervals are unchanged.

Speaker changes require idle audio/timer/player/alarm and closed physical editors. Scan cancellation can stop discovery even if audio becomes busy, but not while a physical editor owns the menu. Ordinary music/speech/alarms are not stopped by a refused command. A list failure disables speaker actions without hiding unrelated timer/alarm controls. Existing audio-output preferences and independent LOCAL/BT volumes remain separate from connecting a speaker. SSP remains automatic; BLE-only or legacy PIN-only audio devices gain no support in this stage.

## Data, commands and limits

`bt_control:true` advertises the feature. The page sequentially reads a separate no-store `/bluetooth.json` after ordinary status. It contains epoch, published command snapshot ID, supported/available/scanning/connected state, target ID, known count and at most sixteen entries (four saved plus twelve discoveries). Entry IDs are twelve hex characters representing the address; entry names use the shared bounded UTF-8/JSON escaping. The existing public read-only status model is retained; no pairing keys, passwords or authorization tokens are published. Response allocation remains 4 KiB per request. The ordinary status is not expanded with the device list.

Authenticated same-origin `/bluetooth` uses the existing token/epoch/ID/nonce envelope. Actions are `scan 0`, `cancel 0`, `disconnect 0`, `connect <peer>` and `forget <peer>`. Peer is a decimal 48-bit address carried in the request's 64-bit expected field, not a row index or name; all 48 bits are exactly representable in JavaScript numbers. Zero, broadcast, overflow, wrong scope and wrong-endpoint requests are rejected. The main loop resolves the current catalog/known registry again before acting. Missing/stale devices return `bt_not_found`; a new device at a full registry returns `bt_registry_full`.

HTTP callbacks queue commands and serialize published snapshots only. No inquiry, pairing, forgetting or Flash operation runs inside a callback. A snapshot acknowledgement prevents premature completion against an old list. Duplicate accepted commands reuse existing results, rather than starting another scan/connect/forget. Physical/USB Forget now shares the same registry mutation helper. No Flash schema/sector, audio asset, gain, phone authorization or Wi-Fi credential change is introduced.

## Verification and acceptance

Native tests cover all command scopes/endpoints, 48-bit IDs, invalid/broadcast/overflow values and duplicate requests. A maximum sixteen-entry escaped-name serializer test verifies fit within 4 KiB including HTTP headroom, output truncation guards and UTF-8 handling. The existing catalog/policy suites retain deduplication/name/manual-OFF coverage. An actual-main-handler fixture checks busy/editor gates, reordered/lowercase addresses, active-peer no-op, full-registry refusal, missing peers, scan cancellation and successful/failed shared Forget without partial registry mutation.

Production JavaScript tests cover stable selection after reorder, lost-response retry, connected versus connecting, disconnect versus forget, scan/cancel OFF, confirmation refusal/acceptance, full slots, stale peers, list-only failure, epoch mismatch and older metadata. Real Chrome tests at 360/412/960 CSS pixels with enlarged text cover connect, scan/cancel, native Forget confirmation, full slots, HTML-like names as text, list failure isolation and no horizontal overflow. Both firmware profiles compile. These fixtures do not establish radio timing, four-client acceptance or peak heap use on hardware.

After separately approved installation, refresh the page. Connect a saved Portable/Nest without scanning; confirm active state and playback, then stop audio. Disconnect and verify no later automatic return. Scan with another speaker in pairing mode, observe results, cancel and confirm OFF. Scan/connect a discovered device, wait for stream ACTIVE and autosave, then verify saved direct reconnect after restart. Confirm Forget cancellation leaves the entry, confirmed Forget removes it and it remains absent after restart. Verify physical-menu changes appear in the page, stale selections are refused and busy audio is not interrupted. Test HOME and direct mode and later four real clients. Restore the intended saved speaker/output after testing. The temporary warning asset still needs manual replacement on both cards and is independent of this firmware stage.
